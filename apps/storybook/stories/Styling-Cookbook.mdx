# Styling Cookbook

Eight recipes for changing how dzup-ui looks, in the order you should reach for
them. Every recipe is a **story that renders** — the code below is copied from
[Compositions/Customization/Overrides](?path=/docs/compositions-customization-overrides--docs)
and `yarn validate:doc-snippets` fails if the two drift apart. Five of them are
also asserted in a real browser, on Chromium, Firefox and WebKit, by
`e2e/components/styling-overrides.spec.ts`.

The ordering is the recommendation. **A recipe further down the list is not a
better tool — it is a narrower one.** If a token can do the job, a token should
do the job.

Each snippet is copied **byte for byte** from the story that renders it, which
is why it arrives wrapped in the story's `template:` — the validator compares
the two exactly, and trimming the wrapper here would mean maintaining a second
copy that nothing executes. Read from the first `<div>` inward.

## 1. Brand theme

**Problem.** The product has its own colour and shape language, and every
component should follow it.

**The one sanctioned mechanism.** Set design tokens on a scope. Nothing else.
No component is touched, no selector is written, and every component — including
ones added after you wrote this — picks it up.

{/* fixture: packages/core/stories/compositions/styling/Overrides.stories.ts#brand-theme */}

```ts
    template: `
      <div
        data-dz-override-fixture="brand-theme"
        style="
          --dz-primary: oklch(0.55 0.21 296);
          --dz-primary-foreground: oklch(0.99 0 0);
          --dz-button-radius: 0px;
          --dz-input-radius: 0px;
          display: grid;
          gap: 12px;
          max-width: 320px;
        "
      >
        <DzButton tone="primary">Branded</DzButton>
        <DzInput model-value="Branded field" />
      </div>
    `,
```

**Set it at `:root`** in your application stylesheet for the whole app; the
inline style above only exists so the story can show a scoped version beside an
unbranded one.

**Note which radius tokens are set.** Not `--dz-radius-md`. `DzButton` reads
`--dz-button-radius` and `DzInput` reads `--dz-input-radius` — an earlier draft
of this recipe guessed the global one, the corners did not move, and a
Playwright assertion caught it. **Read the component's anatomy table rather than
guessing**; every component page lists the tokens it actually reads.

<DoDont>
  <Do>Set `--dz-*` tokens at `:root` or on a scope</Do>
  <Dont>Copy a token's *value* into your own CSS — it will not follow the theme, and dark mode will diverge</Dont>
</DoDont>

## 2. Compact density

**Problem.** The same components, in less vertical space.

**The one sanctioned mechanism.** The spacing scale, plus the `size` recipe.
Components read `--dz-spacing-*` and their own size tokens; changing the scale
moves everything consistently instead of one control at a time.

{/* fixture: packages/core/stories/compositions/styling/Overrides.stories.ts#compact-density */}

```ts
    template: `
      <div
        data-dz-override-fixture="compact-density"
        style="--dz-spacing-2: 0.25rem; --dz-spacing-3: 0.375rem; display: grid; gap: 6px; max-width: 320px;"
      >
        <DzButton size="sm">Compact</DzButton>
        <DzInput size="sm" model-value="Compact field" />
      </div>
    `,
```

<DoDont>
  <Do>Change the spacing scale, and pass `size="sm"` where a smaller control is wanted</Do>
  <Dont>Set a fixed `height` on the component — it fights the size recipe and breaks at other sizes</Dont>
</DoDont>

## 3. One component token

**Problem.** One family is right in every way but one.

**The one sanctioned mechanism.** The component's own `--dz-{component}-*`
token, set at `:root` for the family or inline for one instance.

{/* fixture: packages/core/stories/compositions/styling/Overrides.stories.ts#component-token */}

```ts
    template: `
      <div data-dz-override-fixture="component-token" style="display: flex; gap: 12px;">
        <DzButton>Default</DzButton>
        <DzButton style="--dz-button-disabled-opacity: 0.9;" disabled>
          Barely dimmed
        </DzButton>
      </div>
    `,
```

**Which tokens exist is declared, not guessed.** Each component page carries an
anatomy table listing exactly the tokens it reads. `DzButton` reads 31 of them:

<Anatomy of="DzButton" />

**Not every component has them.** `DzSelect` and `DzTable` declare
`componentTokens: []` — they style from global semantic tokens and own no
`--dz-select-*` or `--dz-table-*` of their own. For those two, recipe 1 changes
the theme and recipe 5 changes one instance; there is no middle option, and the
anatomy table says so rather than leaving you to discover it.

## 4. Recipe variant

**Problem.** A different look is wanted, and the library already has one.

**The one sanctioned mechanism.** `variant`, `size`, `tone` and `density`. The
taxonomies are frozen (ADR-02) precisely so that they are safe to rely on.

{/* fixture: packages/core/stories/compositions/styling/Overrides.stories.ts#recipe-variant */}

```ts
    template: `
      <div data-dz-override-fixture="recipe-variant" style="display: grid; gap: 12px; max-width: 320px;">
        <DzButton variant="outline" tone="danger">Outline · danger</DzButton>
        <DzInput variant="underlined" model-value="Underlined" />
      </div>
    `,
```

The resolved value is mirrored onto the root as `data-variant`, `data-tone`,
`data-size`, so your own CSS can respond to it without knowing a class name.

<DoDont>
  <Do>Pick the variant that exists</Do>
  <Dont>Rebuild an existing variant with your own classes — it will drift from the real one at the next release</Dont>
</DoDont>

## 5. Part override (`ui`)

**Problem.** One node **inside** one component is wrong — a spinner, an error
message, a dialog backdrop, a portaled listbox. No prop reaches it and `class`
only reaches the root.

**The one sanctioned mechanism.** The `ui` prop, keyed by the component's
declared part names.

{/* fixture: packages/core/stories/compositions/styling/Overrides.stories.ts#part-override */}

```ts
    template: `
      <div data-dz-override-fixture="part-override" style="display: grid; gap: 16px; max-width: 420px;">
        <DzButton loading :ui="{ spinner: 'h-6 w-6' }">Oversized spinner</DzButton>

        <DzInput
          model-value=""
          error="This field is required"
          :ui="{ error: 'text-[length:var(--dz-text-sm)] font-semibold' }"
        />

        <DzSelect
          :items="items"
          placeholder="Roomier list"
          :ui="{ content: 'p-3', item: 'py-3' }"
        />

        <DzDialog>
          <DzDialogTrigger as-child>
            <DzButton variant="outline">Blurred backdrop</DzButton>
          </DzDialogTrigger>
          <DzDialogContent :ui="{ overlay: 'backdrop-blur-sm' }">
            <DzDialogTitle>Overridden dialog</DzDialogTitle>
          </DzDialogContent>
        </DzDialog>

        <DzTable caption-visible :ui="{ title: 'text-left font-semibold' }">
          <template #caption>Visible, left-aligned caption</template>
          <DzTableHeader>
            <DzTableRow><DzTableCell header>Fruit</DzTableCell></DzTableRow>
          </DzTableHeader>
          <DzTableBody>
            <DzTableRow><DzTableCell>Apple</DzTableCell></DzTableRow>
          </DzTableBody>
        </DzTable>
      </div>
    `,
```

**Three things worth knowing.**

- **A part name that does not exist is a type error**, not a class that lands
  nowhere. `ui` is typed from the component's own anatomy.
- **Overrides merge through `cn()`** (clsx + tailwind-merge), so `h-6` *replaces*
  the recipe's `h-4` rather than fighting it. **No `!important` is needed** —
  asserted in a real browser on three engines.
- **`ui` reaches places `class` cannot**: the select's listbox renders in a
  portal, outside the component's own tree.

**`class` has not moved.** It still lands where it always did: the button root,
the input's visual field, the select trigger, the dialog panel, the table's
scroll container. `ui.root` is how you reach an outer node.

**Parts are scoped to their component.** `data-part="content"` is the select's
listbox in one place and a `<table>` in another; a selector must say which
component it means. Prefer `ui` over writing the attribute selector yourself.

## 6. Global default

**Problem.** Many instances should share the same settings, and repeating them
is how they drift.

**The two sanctioned mechanisms, and the order between them.** `DzProvider`
sets defaults for the whole application; the group components — `DzButtonGroup`,
`DzInputGroup`, `DzFormField` — set them for a subtree through compound context
(ADR-08). Precedence is fixed by ADR-20 §6 and is the same for every component:
**an explicit prop, then compound context, then the provider, then the
component's own default.** A prop wins because it is what the author of that
line wrote; a group beats the provider because it is nearer and more specific.

{/* fixture: packages/core/stories/compositions/styling/Overrides.stories.ts#global-default */}

```ts
    template: `
      <div data-dz-override-fixture="global-default" style="display: grid; gap: 12px;">
        <DzProvider :defaults="{ DzButton: { size: 'sm', tone: 'info' } }">
          <DzButtonGroup variant="outline">
            <DzButton>Provider size and tone, group variant</DzButton>
            <DzButton tone="danger">Opts out of tone only</DzButton>
          </DzButtonGroup>
        </DzProvider>
      </div>
    `,
```

**What a provider default reaches, stated plainly.** A component honours one
only if it asks for it, and the ones that do declare the axes in their anatomy's
`globalDefaults`. `DzButton` is the first (`size`, `variant`, `tone`); the rest
of the catalog still reads its own props and its group context only, so a
provider default set for a component that has not been wired yet is silently
inert rather than partly applied. The rollout is `TASK-OSS-P4-03` onwards.

`DzProvider` also carries the concerns that have no per-component prop at all —
locale, writing direction, message catalog, portal target, motion policy, CSP
nonce and test ids. Recipe 1 is still the answer for the theme itself.

## 7. Shadow DOM and embedded shells

**Problem.** The components are embedded in a page you do not control — a
widget, a browser extension, a micro-frontend — and the host's CSS must not
reach in, nor yours out.

**The one sanctioned mechanism.** A shadow root, with **both halves handled**:

- **Custom properties inherit through the shadow boundary.** Tokens set on an
  ancestor reach the shadow tree for free.
- **Stylesheets do not.** The component stylesheet has to be adopted into the
  root explicitly.

Missing the second half is the usual failure, and it looks like "the tokens
work but nothing is styled".

{/* fixture: packages/core/stories/compositions/styling/Overrides.stories.ts#shadow-dom */}

```ts
    template: `
      <div data-dz-override-fixture="shadow-dom">
        <div ref="host" />
      </div>
    `,
```

```ts
const root = host.attachShadow({ mode: 'open' })

// Custom properties inherit through the boundary; stylesheets do not.
root.adoptedStyleSheets = [sheetFrom('@dzup-ui/core/styles')]
```

`DzThemeProvider` renders no element of its own (its template is a bare
`<slot />`), so it works inside a shadow root exactly as it does outside.

**The limitation, rather than a workaround presented as a feature: portaled
content escapes the shadow root.** A dialog or select mounted inside teleports
to `document.body`, outside the boundary, and loses the adopted sheet. Pass
`portalTo` to keep it inside the shell. A provider-level portal target is
**fixed in `TASK-OSS-P4-04`**: set `DzProvider`'s `portal` to a container inside
the shadow root and every overlay stays within the boundary. All nineteen
portal-using components honour it, including the four that used to teleport to a
hard-coded `body` with no prop to override. See
[Portals & Embedding](?path=/docs/guides-portals-embedding--docs).

## 8. Anti-patterns

Every mechanism below is forbidden by ADR-19, and each one has a recipe above
that replaces it.

surface this contract exists to keep small.
