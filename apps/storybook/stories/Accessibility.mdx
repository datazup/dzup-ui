# Accessibility

Accessibility is a **contract**, not an afterthought. Every component targets
**WCAG 2.2 AA**, and the Storybook **A11y** panel audits each story live (Deque
axe-core). Under the Vitest addon those same audits run in a real browser as part
of the `storybook-test` CI job.

## The enforced pipeline

The audit is wired as a **CI gate**, configured globally in
`.storybook/preview.ts`:

- **Ruleset** — `a11y.options.runOnly` pins the full **WCAG 2.2 AA** tag set
  (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`). axe's defaults stop at
  2.1, so this explicitly turns on the new 2.2 AA criteria (target size,
  focus-not-obscured, dragging movements, …). `best-practice` rules are excluded
  so the gate maps exactly to the "WCAG 2.2 AA" claim.
- **Report artifact** — the `storybook-test` job runs the audit in-browser and
  publishes the per-story results (with axe violation detail) as the
  `storybook-a11y-report` CI artifact on every run.
- **Gate level (`a11y.test`)** — rolled out **per family**. The default is
  report-only (`'todo'`): violations surface in the panel and the CI report but do
  **not** fail the build. A family flips to blocking by opting into
  `a11yError` (`stories/_shared/a11y.ts`) once its stories audit clean; from then
  on any violation in that family **fails the PR**.

axe-core automatically catches roughly ~57% of WCAG issues — the gate makes that
57% non-regressable **for enforced families**. The remaining criteria still
require the manual [authoring checklist](#authoring-checklist) below.

> **Why per-family?** The audit runs in a real browser via
> `@storybook/addon-vitest`. Enabling it globally at `'error'` today would fail
> the job on a backlog of pre-existing violations (see below), so families are
> cleaned and flipped one at a time. **Target end-state:** every family enforced,
> then the global default flips to `'error'`.

## The per-family rollout recipe

This is the checklist that flipped Cards. Every subsequent family is a repeat of
it, not a fresh investigation.

1. **Clear story token debt first.** `yarn codemod:story-colors` then
   `yarn validate:tokens`. Raw Tailwind grays were the single largest source of
   `color-contrast` findings; auditing before this step wastes the pass.
2. **Measure, don't guess.** Temporarily set `a11y.test: 'error'` in
   `.storybook/preview.ts`, run `yarn workspace @dzup-ui/storybook test-storybook
   --reporter=json --outputFile=audit.json`, and count failures per family. Revert
   the global afterwards.
3. **Fix the root, not the report.** If the failing node is rendered by a
   component, fix the component's `*.variants.ts` — patching the story would
   silence the finding while shipping the bug. If it is the story's own markup,
   fix the story.
4. **Spread `a11yError`** into every story meta in the family, importing it from
   `../_shared`.
5. **Prove the gate bites.** Introduce a violation on purpose, watch the
   `storybook-test` job fail, revert.
6. **Update this table** with the real number.

## Known a11y debt (from the enforced audit)

Running the gate at `'error'` across every family surfaces the remaining
pre-existing violations. The dominant classes:

- **`color-contrast` (largest: 132 of the 207 failing stories, 2026-07-16)** —
  the root cause is using `--dz-{intent}` as a **text** colour. `--dz-{intent}`
  is a fill and border colour, measuring only 3.69–4.38:1 against
  `--dz-background` in light. The correct text token is
  `--dz-{intent}-muted-foreground` (7.31–10.25:1). This is stated as rule 1b in
  `CLAUDE.md` and enforced for the intent-on-muted pair by
  `yarn validate:tokens`.
- **Structural ARIA** — `aria-allowed-attr`, `aria-required-parent`,
  `aria-required-children`, `nested-interactive` in composite widgets
  (tabs, menu, listbox, tree, stepper, tables).
- **`scrollable-region-focusable` (38 stories)** — a `<pre>` with
  `overflow-x-auto` must be keyboard-reachable (`tabindex="0"`).
- **Labelling** — `label` (19), `button-name` (18): demo controls in stories
  without an accessible name.
- **`target-size` (WCAG 2.2 AA, 5 stories)** — some `xs`/`sm` controls fall below
  the 24×24px minimum touch target.

> **A token defect this audit found — now fixed:** `--dz-warning-foreground` on
> `--dz-warning` used to measure **3.51:1** in light (warning sat at shade 500) —
> a solid fill pair that failed AA. `--dz-warning` is now pinned to shade 400 in
> both themes, so the pair measures **5.87:1** and the DESIGN.md contrast gate
> asserts it. `--dz-warning-solid` (8.44:1) remains the max-contrast fill
> components render uniformly across every intent.

## Escape hatches (use sparingly, always documented)

Two documented ways to keep a family gating while handling a specific case, both in
`stories/_shared/a11y.ts` — each **must** carry a comment explaining why.

```ts
import { a11yError, a11yDisableRules } from '../_shared'

// Opt a clean family into enforcement (spread into every story meta in the family).
const meta = {
  title: 'Core/Buttons/DzButton',
  parameters: { ...a11yError },
} satisfies Meta<typeof DzButton>

// Disable one SPECIFIC rule for a documented false positive, staying gated.
export const DecorativePlaceholder: Story = {
  // Placeholder bars are decorative and intentionally low-contrast.
  parameters: { ...a11yDisableRules('color-contrast') },
}
```

Never blanket-disable the audit (`a11y: { test: 'off' }`) to silence a real
regression — fix the component or the story instead.

## Contract a11y props

Every interactive component extends `BaseAccessibilityProps` from
`@dzup-ui/contracts`, exposing a consistent set of hooks:

<DocTable
  head={['Prop', 'Purpose']}
  align={['left', 'left']}
  rows={[
    ['`id`', 'Stable element id (label association)'],
    ['`ariaLabel`', 'Accessible name when no visible label'],
    ['`ariaLabelledby`', 'Reference an external labelling element'],
    ['`ariaDescribedby`', 'Reference help/error text'],
  ]}
/>

Stateful components additionally manage the right ARIA state for you, e.g.
`aria-busy` while `loading`, `aria-pressed` on toggles, `aria-invalid` on invalid
form controls, `aria-current` on active navigation items.

## Authoring checklist

- **Name** — every control has an accessible name (visible label, `ariaLabel`, or
  `ariaLabelledby`).
- **Keyboard** — all interactions are reachable and operable by keyboard; focus
  order is logical and focus is visible.
- **State** — dynamic state is exposed via ARIA (`aria-expanded`, `aria-selected`,
  `aria-current`, live regions for async/toast).
- **Contrast** — text meets AA (4.5:1; 3:1 for large text) in **both** themes —
  verify with the dark-mode story.
- **Portals** — overlays rendered in a portal may need a `play()` to open them so
  the audit can reach the content.

## Testing a11y in stories

Pair an interaction `play()` with the audit so the addon scans the **interacted**
state, not just the initial render:

```ts
export const OpenMenu: Story = {
  play: async ({ canvasElement }) => {
    const canvas = within(canvasElement)
    await userEvent.click(canvas.getByRole('button', { name: /open/i }))
    // a11y audit now sees the expanded menu
  },
}
```
