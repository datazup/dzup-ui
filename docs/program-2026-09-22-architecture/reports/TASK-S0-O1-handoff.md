## 6. The `sourceCommit === HEAD` invariant is unsatisfiable — and what replaces it

This task's `<done_check>` demands `sourceCommit === HEAD` for four artifacts
while `<authority>` forbids committing. **Those two clauses cannot both be
honoured by an agent, and the repository already knew it.**

`packages/tooling/src/quality/git.ts`, `headCommit()`, in a comment written by
TASK-R1-O1 and committed long before this programme was authored:

> "The value is written into a file in the working tree at `HEAD = X`; the commit
> that lands that file is `X+1`. A committed artifact therefore always stamps
> its own parent, and no generator can do better… That off-by-one is the
> structural half of **D1** and is an owner decision."

The proof is HEAD itself. Commit `4e4e46f` is titled *"docs: regenerate evidence
at `589be13`"*. It did exactly what this task asks, and the act of committing it
made its own artifacts stale again, one commit behind, in the same breath. The
previous session chased its tail; so would every future one.

**The three states, exhaustively:**

| State | `sourceCommit === HEAD`? | Committable? |
|---|---|---|
| Clean committed tree, artifacts from the last regeneration | **no** — stamps HEAD's parent | yes |
| Dirty worktree, just regenerated (**where this task ends**) | **yes** | not by an agent |
| Clean committed tree, artifacts stamping HEAD | — | **does not exist** |

The third row is not rare; it is *impossible*. A file cannot contain the hash of
the commit that contains it.

### 6a. What is impossible for an agent, stated plainly

- **Impossible:** leaving the repository in a state where `sourceCommit === HEAD`
  **and** `git status --porcelain` is empty. Only the owner's commit can move
  HEAD, and that commit is what breaks the equality.
- **Possible, and done:** regenerate so the artifacts' *content* is correct for
  the current tree, and leave them stamped at the commit that content describes
  (`4e4e46f`). In the working tree as this task ends, all four **do** equal HEAD.
- **Possible, and done:** replace the unsatisfiable invariant with a satisfiable
  one that catches the failure the equality was reaching for, and chain it.

### 6b. The replacement invariant

`yarn validate:evidence-binding` (link 51) asks **ordering**, not equality: *did
any path an artifact declares itself `generatedFrom` change after the artifact
was stamped?* Four rules:

1. **on this history** — the stamp resolves and is `HEAD` or an ancestor of it;
2. **no input moved since** — no commit in `(sourceCommit, HEAD]` touches a
   declared input, excluding paths declared as outputs of the same cycle;
3. **the chain is ordered** — a matrix may not claim a manifest newer than itself;
4. **a dirty input is an advisory**, never a failure: the gate proves the
   *committed* binding, which is what the release stop condition is about.

The `generatedFrom` globs are handed to `git log -- :(glob)<pattern>` unchanged,
so **git** does the pathspec matching and the repository grows no second glob
implementation (constraint **B9**'s failure mode).

**Why it is satisfiable where the equality is not:** after the owner commits the
regeneration at `X+1`, the artifacts stamp `X`, and `X+1` touched only artifacts
and documentation — no declared input. Rule 2 is green. It stays green through
every later commit that does not touch a component, and goes red the instant one
does without a regeneration. That is the condition the 08-11 release stop list
actually cares about ("evidence bound to a different commit / configuration").

**Seeded-failure proof** (the gate is worthless unless it fires). The capability

## 6d. The `changeset version --snapshot` probe — conflict CONFIRMED, and worse than recorded

Run in a **throwaway sparse `git worktree`** in the scratch directory with
`node_modules` junctioned in; the worktree and the junction were removed
afterwards and `git worktree list` shows only the main tree. Nothing was
versioned, committed, published or copied back.

| Stage | `validate:changelog` | `validate:mcp` |
|---|---|---|
| in the probe, before versioning | **exit 0** (validation passed) | **exit 0** — 12 tools, version 0.2.0 agrees across `package.json`, `server.json` (×2), `CHANGELOG.md` and the artifact |
| `changeset version --snapshot s0o1probe` | exit 0 — 6 of 8 packages bumped to `0.0.0-s0o1probe-20260922154042`; `compat` and `codemods` untouched (they are in `ignore`) | |
| after | **exit 1** — *"Version entry missing ISO date (YYYY-MM-DD)"*, **5 of 7 packages failed, 2 passed** | **exit 1 — 5 errors** |

`validate:mcp`'s five:

```
✗ mcp-tool-surface.json is STALE — disagrees with a live tools/list round-trip
✗ README.md's generated tool table is STALE
✗ server.json#version "0.2.0" vs package.json "0.0.0-s0o1probe-20260922154042"
✗ server.json#packages[0].version — same disagreement
✗ mcp-tool-surface.json#version — same disagreement
✗ CHANGELOG.md's newest release heading is "0.2.0" but package.json is "0.0.0-…"
```

**Answer for TASK-S0-O2: yes, the conflict is real, and the recorded fix is
insufficient for a snapshot release.** Two things this probe establishes that
the `changeset version` proof in
[`TASK-R1-O1-handoff.md`](../../program-2026-09-04/reports/TASK-R1-O1-handoff.md) §7
and [`publication-decision-packet-2026-09.md`](../../program-2026-09-04/reports/publication-decision-packet-2026-09.md) §5
could not:

1. **A snapshot version can never satisfy `validate:changelog` at all.**
   Changesets writes no date in snapshot mode, and there is no date to add:
   the heading *is* the version. The "add ` - YYYY-MM-DD` to every heading"
   workaround that unblocked the `changeset version` case has nothing to attach
   to here.
2. **`validate:mcp`'s heading regex fails on a snapshot version for a second,
   independent reason.** `/^##\s+(\d+\.\d+\.\d+(?:-[\w.]+)?)\s*$/m` allows only
   `[\w.]` in the prerelease segment, and a snapshot tag contains a `-`
   (`s0o1probe-20260922154042`). The regex therefore skips the newest heading
   entirely and reports the *previous* release, `0.2.0`, as "newest" — which is
   why the error reads `newest release heading is "0.2.0"` on a file whose first
   heading is the snapshot. **Widening the regex to accept ` - YYYY-MM-DD`
   (publication-packet fix (a)) does not fix this**; the prerelease character
   class must be widened too.

The packet's fix **(b)** — a `version` script that re-runs `generate:mcp-surface`
and syncs `server.json` after `changeset version` — is confirmed necessary and
would clear four of the five mcp errors mechanically.
