## 1. Message syntax

Catalog strings are plain text, or — when they carry a value — a documented
**subset of ICU MessageFormat**, the format translation-management tools
(Crowdin, Weblate, Lokalise, Phrase) already read.

| Form | Example | Meaning |
|---|---|---|
| text | `Clear input` | rendered as is |
| argument | `{duration} remaining` | the value; a **number** is formatted for the locale (`1,234` in `en`, `1.234` in `de`) |
| plural | `{count, plural, one {# tag} other {# tags}}` | branch chosen by `Intl.PluralRules` (cardinal) for the locale; `#` is the number, formatted |
| exact match | `{count, plural, =0 {No tags} other {# tags}}` | `=N` wins over the category |
| ordinal | `{place, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}` | `Intl.PluralRules` with `type: 'ordinal'` |
| select | `{kind, select, file {File} other {Item}}` | exact string match |
| quoting | `Use '{braces}' literally` · `It''s` | ICU apostrophe rules: `'` only quotes before `{`, `}` (or `#` inside a plural); `''` is one apostrophe; "don't" needs no escaping |

Rules the parser enforces, with a syntax error rather than a guess:

- every `plural`, `selectordinal` and `select` has an `other` branch;
- plural selectors are `zero`, `one`, `two`, `few`, `many`, `other` or `=N`;
- no duplicate selectors, no unclosed `{`, no stray `}`, no unterminated quote;
- **not supported:** `offset:`, and the `number` / `date` / `time` argument
  types. A date inside a message would bypass the semantics in §3; format it
  with `useDzFormats()` and pass the result as a string argument.

**Plural categories are the locale's, not English's.** English has `one` and
`other`. Bosnian adds `few` (2–4, 22–24, …), Arabic uses all six, French puts `0`
in `one`, Japanese has only `other`. A translation writes the branches its
language needs; `message-format.spec.ts` asserts `bs`, `fr` and `ar` behaviour.

### Typed messages

A count-bearing key is declared in Core's `DzMessageCatalog` augmentation as
`DzMessage<Args>` (from `@dzup-ui/contracts`):

```ts
DzTagsInput: {
  count: DzMessage<{ count: number }>
  countOfMax: DzMessage<{ count: number, max: number }>
}
```

Formatting it without a numeric `max` is a **type error** at the call site. A
plain string is still assignable to every `DzMessage`, so a host catalog and a
translator's JSON never need a cast. `DzMessageKey` is the union of every dotted
key (`'DzInput.clear' | …`) the loaded tiers declare.

### Count-bearing messages in the catalog

Each of these was an English concatenation (`` `${n} tag${n === 1 ? '' : 's'}` ``)
in a `<script>` block before TASK-R5-O4 — outside the catalog, and outside what
`validate:hardcoded-strings` reads.

| Component | Keys | Where it renders |
|---|---|---|
| `DzCountdown` | `days`, `hours`, `minutes`, `seconds` (plural), `remaining` (`{duration}`), `finished` | polite live region; units joined by `Intl.ListFormat` (`unit`, `long`) |
| `DzDataView` | `showingAll` (plural), `showingRange` (plural on `total`), `loading` | polite live region |
| `DzMention` | `suggestionsAvailable` (plural) | status region while the menu is open |
| `DzRating` | `starTitle` (plural) | each star's `title` |
| `DzTagsInput` | `count`, `countOfMax` (plural) | polite live region |

English output is identical below 1,000, with one deliberate fix: `DzDataView`'s
paged announcement said *"of 1 items"*.

**Still outside the catalog** (measured; not this task's scope, listed so the
next packet does not re-derive it): `DzDataGridPagination` ("Showing … to … of …",
`n / page`), `DzDataGridHeader` (`Filter {header} by …`), `DzDataGridBody`
(`Select row n`), `DzOrderList` (three drag announcements), `DzLightbox`
(`Image n of m`), `DzImageComparison` (`n% of the after image revealed`),
`DzRating` (`aria-valuetext` `n of m`), `DzRangeSlider` (`Range minimum/maximum`),
`DzColorModeToggle` (`Switch to … theme`), `DzMention` (`{char} suggestions`),
`DzPersonaSelector` (`{name} avatar`), `DzFileUpload` (`Remove {name}`). They are
template-literal bindings or script strings, which `validate:hardcoded-strings`
does not read. `DzFileUpload`'s four `error` event `reason` strings (including
*"Maximum 1 files allowed"*) are event **payload**, not rendered by Core — a host
may match on them, so translating them is an API decision, not a string change.

## 2. Formatting, fallback and escaping

Inside Core, components format through an internal per-component helper. Outside
Core — a Pro component's own keys, or an application's — use the public
composable:

```ts
import { useDzMessageFormat, useDzMessages } from '@dzup-ui/core'

const { read } = useDzMessages()
const { format } = useDzMessageFormat()
const label = format(
  read('DzChart.points', '{count, plural, one {# point} other {# points}}'),
  { count: points.length },
  '{count, plural, one {# point} other {# points}}', // the shipped English default
)
```

It is also exported from `@dzup-ui/core/i18n`.

**Fallback rule.** Overrides resolve **per key** (a host translating
`DzTagsInput.count` keeps every other English string). A translation that does
not parse, or names an argument the component does not pass, renders the
**English default** instead of breaking the component, and warns once in
development. The English default's branches are chosen by **English** plural
rules whatever the application locale, while its numbers group for that locale —
an untranslated key in a French application says "0 tags", not "0 tag".

**Plural rules are cached** per locale and type in `intl-cache.ts`
(`cachedPluralRules`), beside the number, date, relative-time and list
formatters; parsed messages are cached by source.

**Escaping rule.** Argument values are **data**:

1. they are inserted after parsing, so a value containing `{`, `}`, `#` or `'` is
   never read as message syntax;
2. the formatter's only output is **text** — it never produces markup — and Core
   renders that text through Vue text and attribute bindings, which escape `<`
   and `&`. Core has **zero** `v-html` / `innerHTML` sinks;
3. code that must put a formatted message into HTML passes it through the
   sanitizer seam (`useDzSanitizer`, `DzProvider :sanitizer`), whose default
   escapes.

`message-format.spec.ts` proves all three with a hostile value
(`<img src=x onerror="alert(1)"> & {count, plural, other {#}} '#'`) in a text
node, an attribute and the escaping default. There is deliberately no
"escape to HTML entities" default: bound as text, `&lt;` would render literally.

**Pseudo-locale.** `pseudoMessages()` (the Storybook *Pseudo-locale* toolbar)
rewrites only the translatable text of a message — argument names, selectors and
`#` survive — so the pseudo catalog still formats, and `validate:i18n-packs`
checks it with the same rules as a real pack.

## 3. Instant vs plain date semantics

Two kinds of date value exist, and confusing them moves a user's data by a day or
an hour:

- an **instant** (`DzInstant` — `Date`, epoch ms, or ISO 8601 **with** an offset
  or `Z`) is a moment on the global timeline. It has no wall-clock value until it
  is rendered **in a time zone**;
- a **plain** value (`DzPlainDate` — `YYYY-MM-DD`; `DzPlainTime` — `HH:mm` /
  `HH:mm:ss`) is a calendar date or wall-clock time with **no** zone. A birthday
  picked in Sarajevo is the same day in New York; a 09:00 opening time is 09:00.

**The rule:** a host's `DzProvider :formats="{ date: { timeZone } }"` applies to
instants and **never** to plain values.

| Component / API | Value | Kind | Time-zone handling | Typed as |
|---|---|---|---|---|
| `DzCalendar` | `v-model:value`, `v-model:focusedDate`, `minDate`, `maxDate` — `YYYY-MM-DD` | plain date | Converted to `@internationalized/date` `CalendarDate`; weekday layout computed in the runtime's zone from a plain date, which is zone-independent. `disabledDate(date: Date)` receives a **local-midnight** `Date` — read it with local getters (`getDate()`), never UTC getters. "Today" is the runtime's local date. Host `timeZone` not applied. | `string` (`DzPlainDate` names the semantics) |
| `DzDatePicker` | `v-model` — `YYYY-MM-DD`; `min`, `max` | plain date | `CalendarDate` through Reka's date field, segments in the resolved locale. Host `timeZone` not applied. | `string` |
| `DzDateRangePicker` | `v-model` — `{ start, end }` of `YYYY-MM-DD` | plain date | As `DzDatePicker`, per end. | `DateRangeValue` of `string` |
| `DzTimePicker` | `v-model` — `HH:mm` / `HH:mm:ss`, 24-hour | plain time | Displayed by formatting a **UTC-built** value **in UTC** (`timeZone: 'UTC'` passed as the caller's option, which wins over host defaults). Host `hour12`/`hourCycle` defaults still apply. **Fixed in TASK-R5-O4:** it used a local `Date` merged with the host's defaults, so a host `timeZone` shifted the time shown (09:05 → 22:05 for a Sarajevo user under `Pacific/Kiritimati`). | `string` |
| `DzRelativeTime` | `value` — `Date`, epoch ms, ISO string | instant | Relative phrase from the millisecond difference (zone-independent). The absolute tooltip is formatted with the host's `formats.date` — **zone applied**. | `RelativeTimeValue` (= `DzInstant`) |
| `useRelativeTime`, `formatRelativeTime`, `formatAbsoluteTime` | same | instant | As `DzRelativeTime`; the pure helpers use the runtime locale when `locale` is omitted. | `RelativeTimeValue` |
| `DzCountdown`, `useCountdown` | `target` — `Date` or epoch ms with `mode: 'to'`; a span in ms with `mode: 'duration'` | instant / duration | Remaining time is a duration; no zone. The announcement is count-bearing (§1). | `Date \| number` |

**What the types enforce, and what they cannot.** `DzInstant`, `DzPlainDate`
and `DzPlainTime` are exported from `@dzup-ui/contracts`. The plain aliases are
`string`, not template-literal types: narrowing today's `string` props to
`` `${number}-${number}-${number}` `` would reject every consumer variable typed
`string` — a breaking (`minor`) change for a documentation gain, recorded as an
owner decision rather than made here. Enforcement at the formats layer is
behavioural and spec-backed (`temporal-semantics.spec.ts`): plain values pin
their zone as the caller's option, instants inherit the host's.

**Pitfall for hosts:** an ISO string **without** an offset is an instant only by
accident. ECMAScript parses `2026-06-14` as UTC midnight but
`2026-06-14T09:00` as **local** time. Pass instants with `Z` or an offset.

## 4. Locale packs

A locale pack is **JSON data**, not code:

```json
{
  "locale": "de",
  "direction": "ltr",
  "fallback": ["DzAlert.close", "…"],
  "messages": { "DzInput": { "clear": "Eingabe löschen" } }
}
```

| Field | Rule |
|---|---|
| `locale` | BCP-47 tag; the file is `<locale>.json` |
| `direction` | declared, never inferred; must agree with `directionForLocale()` (`packages/core/src/i18n/direction.ts`) |
| `messages` | translated strings, nested by component group; partial is fine |
| `fallback` | every catalog key **not** translated, listed explicitly — it renders English |

**Loading one:**

```ts
import de from '@dzup-ui/core/i18n/locales/de.json' with { type: 'json' }
```

```vue
<DzProvider :locale="de.locale" :messages="de.messages">
```

`DzProvider` resolves `direction` from `locale` by default; pass
`:direction="de.direction"` to take the pack's declaration instead.

**Tree-shaking.** Packs are copied to `dist/i18n/locales/` as files and imported
by nothing in the library. A consumer who never imports `de.json` never ships
German; the English defaults are already inside the components.
`validate:i18n-packs` fails if any source module imports a pack.

**Published packs.** `@dzup-ui/core/i18n/locales/en.json` — the complete English
catalog, generated from `enMessages` — is the reference a translator or a
translation tool reads. **A scaffold (nothing translated) is not published** by
the build and has no `exports` entry, because importing it would render English
while looking like a translation. Each published pack has its own explicit
`./i18n/locales/<locale>.json` export.

| Pack | Status at `4e4e46f` | Completeness | Published |
|---|---|---|---|
| `en` | complete — 116 / 116 | source (100 %) | yes |
| `de` | **scaffold — 0 / 116 translated, 116 explicit fallback**; awaiting a human translator (never machine translation) | **0 %** — declared, decision **D59** | no |

**Completeness is not the same number as "translated".** A value byte-identical
to its English source is not counted as translated, so a pack that copied English
under every key reads **0 %**, not 100 %. That is why the supported threshold is
**95 % and not 100 %**: a handful of values are legitimately identical (`OK`,
`Email`, `PDF`, a proper noun), and the alternative — an allowlist saying "this
English word really is German" — is exactly the kind of record that stops meaning
anything. Five per cent of headroom absorbs the honest cases and absorbs nothing
else.

### The gate: `yarn validate:i18n-packs`

A `validate:all` link. Per catalog key: translated **or** an explicit fallback,
never neither, never both; no unknown or duplicate keys; every translation parses
and reads the same arguments as English (a plain `{count}` and a plural on
`count` are interchangeable; dropping `{max}`, inventing `{name}` or turning a
plural into a select is not). Per pack: exact shape, file name, declared
direction. Across packs: `en.json` byte-identical to `enMessages`; the generated
pseudo-locale formats; no source module imports a pack; `exports` names exactly
the published packs.

### The second gate: `yarn validate:i18n-completeness`

The gate above asks whether a pack is *structurally* valid. It exits 0 for a pack
that copied English into all 116 values, and for a 0 % scaffold that a release
note then calls a supported locale. This one asks the other question — **how much
of this locale is really translated, is it right for its own plural rule set, and
does its script have a typeface** — and prints a table:

```
| Locale | Dir | Keys | Translated | Identical-to-en | Missing | Arity errors | Plural-category errors | Completeness |
| de     | ltr |  116 |          0 |               0 |       0 |            0 |                      0 | 0 % (scaffold — decision D59) |
| en     | ltr |  116 |          — |               — |       0 |            0 |                      0 | source (100 %) |

locales at >= 95 % completeness: 1 (en) — floor 1
```

Four rules fail the build:

- **`plural-categories`** — a translated plural that omits a category **your
  locale** requires. The required set comes from
  `Intl.PluralRules(locale).resolvedOptions().pluralCategories`, so it is CLDR
  and not a list anyone here maintains. This is the rule worth knowing about
  before you start: a Polish pack declaring only `one` and `other` parses,
  satisfies every rule of `validate:i18n-packs`, and at run time renders the
  `other` branch for `few` (2–4) and `many` (5+) — wrong Polish, silently. Arabic
  needs six branches and would fall through on four. An `=N` exact selector does
  not count as a category (`=1` matches exactly one; Russian's `one` also matches
  21, 31, 101). A category your locale never selects is reported as unused and
  does not fail.
- **`undeclared-scaffold`** — a pack below 95 % that is not named in
  `packages/tooling/src/validators/i18n-completeness-ceilings.json` with the
  decision that made it incomplete. An unfinished locale is fine; an unfinished
  locale nobody wrote down is not.
- **`stale-declaration`** — the converse: a register entry for a pack that has
  since reached the threshold, or for a pack that no longer exists.
- **`supported-floor`** — the count of locales at ≥ 95 % fell below the recorded
  floor. The floor may only rise; raising it is how a finished translation records
  its arrival.

**Script and typeface findings never fail it.** `@dzup-ui/core` vendors no font —
`0` binaries tracked, re-measured on every run — so Arabic, Persian, Urdu and
Hebrew text is drawn in whatever the platform substitutes. That is a deliberate
position (decision **D63**, sheet in
`docs/program-2026-09-22-architecture/reports/TASK-S5-O1-typeface-decision.md`),
so the gate reports it on every run instead of either failing or letting it
disappear. The moment a `--dz-font-family-arabic` token exists in
`@dzup-ui/tokens`, the same row reads `token-provisioned` with no edit anywhere.

## 5. Contributing a locale pack

**The short version:** `yarn i18n:new fr` → translate → `yarn i18n:check` → it
prints a percentage. 116 keys, most of them two or three words; the ten
count-bearing ones need your language's plural branches.

1. **Start from a scaffold:** `yarn i18n:new <bcp47-tag>` — writes
   `packages/core/src/i18n/locales/<tag>.json` with every key listed in
   `fallback`, nothing translated, `direction` resolved for you, and it refuses to
   overwrite an existing pack. (For `de` it already exists.) The older spelling
   `yarn generate:i18n-packs --scaffold <tag>` is the same command.
2. **See what a translation has to survive, before writing one.** Run Storybook
   (`yarn storybook`) and use the two toolbar controls: **Pseudo-locale** renders
   every string accented, padded +30 % and framed in `[!!! !!!]`, which is how you
   find a layout that only fits English; **Direction: RTL** renders every story
   right-to-left under an Arabic locale. Both work with no translation at all, so
   this is the *first* step, not the last — a layout defect found here costs
   nothing, and the same defect found after 116 strings are translated costs the
   translation.
3. **Translate from `packages/core/src/i18n/locales/en.json`.** For each key you
   translate, add it under `messages` and **remove it from `fallback`**. Keep the
   argument names exactly. Partial packs are welcome — untranslated keys stay in
   `fallback` and render English.
4. **Write the plural branches your language needs, not English's** (§1). English
   has two categories, so all ten count-bearing messages read `one` / `other`;
   Polish needs `one few many other`, Arabic `zero one two few many other`,
   Japanese only `other`. `validate:i18n-completeness` checks this against CLDR
   and names the missing branches — you do not have to know the rule set by heart,
   but you do have to run the gate.
5. **No machine translation.** A pack is reviewed by someone who reads the
   language. Say in the pull request who that is. A string produced by a process
   that does not read the language is not a translation, it is a claim that the
   locale is supported — which is worse than an empty `fallback` entry, because the
   `fallback` entry is honest.
6. **Run the gates:** `yarn i18n:check` — structure, then completeness. It names
   every problem by rule and key and prints your pack's percentage. 95 % is
   "supported"; below that the pack must be named in the scaffold register with a
   reason.
7. **Publish it** once at least one key is translated: add
   `"./i18n/locales/<locale>.json": "./dist/i18n/locales/<locale>.json"` to
   `packages/core/package.json` `exports` (the gate fails until you do), and add a
   `patch` changeset for `@dzup-ui/core`. When it reaches 95 %, raise
   `minSupportedLocales` in
   `packages/tooling/src/validators/i18n-completeness-ceilings.json` and remove its
   scaffold entry — that is the change that makes "two locales ship" a gated fact
   rather than a sentence in a release note.
8. **When the catalog grows,** `yarn generate:i18n-packs` rewrites `en.json` and
   adds each new key to every pack's `fallback` — it never translates and never
   deletes a translation.

**Right-to-left locales.** `yarn i18n:new ar` resolves `direction` to `rtl` for
you; the per-component contract is in `rtl-matrix.md` (generated from each
component's `anatomy.ts` `rtl` field, gated by `yarn validate:rtl`), and one
landing route is proved right-to-left end to end in
`apps/landing/e2e/rtl.spec.ts`. Core ships **no Arabic or Hebrew typeface** — `0`
font binaries, re-measured by `yarn validate:i18n-completeness` on every run — so
the typography of an RTL application is the host's responsibility today. Set your
own face on the `sans` token and pin a line height; the decision sheets are
`docs/program-2026-09-22-architecture/reports/TASK-S5-O1-typeface-decision.md`
(current, with licences and measured size costs) and
`docs/program-2026-09-04/reports/TASK-R5-O4-typeface-decision.md` (the original
options table).
