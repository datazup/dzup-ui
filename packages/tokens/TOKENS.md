# Token contract — what is stable, and what is interchange

`@dzup-ui/tokens` publishes the same design system twice. The two are not
interchangeable, and which one you depend on determines what we owe you.

| | Artifact | Import | Role |
|---|---|---|---|
| **Runtime ABI** | `dist/tokens.css` | `@dzup-ui/tokens/css` | The `--dz-*` CSS custom properties. What components read, what you override, what compatibility is measured against. |
| **Interchange** | `dist/tokens.dtcg.json` | `@dzup-ui/tokens/dtcg` | A [DTCG Format 2025.10](https://www.designtokens.org/tr/2025.10/format/) projection of the same source maps, for design tooling. Derived. Never authoritative. |

---

## 1. `--dz-*` is the ABI

**The stable, governed surface of this package is the set of `--dz-*` custom
property names and the values they resolve to.** Everything else — the
TypeScript maps, the Tailwind theme object, the DTCG JSON, the group paths
inside it — is a projection that exists to serve that surface.

Concretely, this is what "ABI" buys you:

- A `--dz-*` name is not renamed or removed without a version bump that says so.
  `--dz-sidebar-text` and `--dz-sidebar-text-hover` are the current deprecations;
  they carry `$deprecated` in the DTCG export and are removed in the next major.
- `var(--dz-primary)` in your own stylesheet is a supported integration. You do
  not need to import anything from JavaScript to use this design system.
- Library CSS ships inside `@layer dz-tokens`, so your unlayered CSS overrides it
  without `!important`. Overriding a `--dz-*` property on `:root` — or on any
  subtree — is the supported way to re-theme.

**What "governed" means today, honestly:** this package is `0.x`. The 0.x
release policy for `@dzup-ui/*` is an open packet (`TASK-N5-01`), so the
sentence above describes the *intent* the token pipeline is built to hold and
the gates that enforce it inside the repository — it is not yet a published
semver guarantee. Treat this section as a statement of contract, and the release
policy as the thing that will make it a promise.

### What is *not* the ABI

- The DTCG group paths (`primitive.color.primary.500`). They are derived from
  the CSS names, not the other way round.
- The `$extensions["com.dzup"]` payload, including `untyped`, `coverage` and
  `themeVarying`. Useful, but shaped for tools, not frozen.
- Which tier a token is declared in. `--dz-appshell-header-bg` moving between
  the semantic and component tiers is not a breaking change; changing its
  resolved value is.

## 2. The DTCG export

```
packages/tokens/dist/tokens.dtcg.json   ·   @dzup-ui/tokens/dtcg
```

- **Spec:** DTCG Format module `2025.10` (Stable, published 2025-10-28). The file
  declares `"$schema": "https://www.designtokens.org/schemas/2025.10/format.json"`
  and validates against that published schema.
- **Generated by:** `yarn generate:tokens:dtcg` (and by `yarn workspace
  @dzup-ui/tokens build`). Output is deterministic and timestamp-free: run it
  twice, diff the bytes.
- **Gated by:** `yarn validate:tokens:dtcg`, which resolves every alias with an
  independent reader and asserts each resolved value equals what `tokens.css`
  computes for the same `--dz-*` name, in both theme cascades. A name present on
  one side and absent from the other fails by name.
- **Never edit it.** It is regenerated from `packages/tokens/src/`.

### Structure

Three groups, mirroring the three tiers:

```
primitive/                    409 tokens — raw ramps and scales
  color/{palette}/{shade}       --dz-colors-{palette}-{shade}
  spacing/ fontSize/ radius/ …
semantic/
  light/                      115 tokens — the `:root, [data-theme="light"]` block
  dark/                       123 tokens — the `[data-theme="dark"]` block
component/                    153 tokens — the component `:root` block
  button/ control/ input/ card/ badge/ dialog/ sidebar/ appshell/ page-hero/
```

Every token carries its ABI name, so you never have to reconstruct it:

```json
{
  "semantic": {
    "light": {
      "primary": {
        "$type": "color",
        "$value": "{primitive.color.primary.500}",
        "$extensions": {
          "com.dzup": {
            "cssVariable": "--dz-primary",
            "cssValue": "var(--dz-colors-primary-500)"
          }
        }
      }
    }
  }
}
```

Semantic→primitive and component→semantic references are emitted as DTCG
aliases (`{group.token}`), **not** resolved values — 319 of them. Flattening
them would throw away the structure that makes the system re-themeable.

### Themes

The DTCG Format module has no modes or themes concept, and there is no Resolver
module in the [technical reports index](https://www.designtokens.org/technical-reports/).
So the two dzup-ui themes are emitted as two sibling groups, `semantic.light`
and `semantic.dark`, mirroring the two CSS declaration blocks one-for-one.
`semantic.dark` additionally carries the eight `--dz-shadow-*` values the dark
block overrides, because that is what the stylesheet does.

Component-tier tokens alias into `semantic.light` (the `:root` default) and are
flagged `themeVarying: true` when their resolved value actually differs under
dark — 29 of them. **If you resolve this export for a dark UI, you must follow
the dark declaration of any ABI name `semantic.dark` redeclares.** That includes
tokens that alias a *primitive*: `--dz-card-shadow` → `--dz-shadow-md` is
theme-varying even though it never touches the semantic tier.

### `$type` mapping

| dzup-ui family | `$type` | Note |
|---|---|---|
| `--dz-colors-*`, all semantic colours, component colours | `color` | `colorSpace: "oklch"`, components `[L, C, H]`, `alpha` only when the CSS carries one |
| `--dz-spacing-*`, `--dz-text-*`, `--dz-radius-*`, `--dz-breakpoint-*`, component sizes | `dimension` | `px` / `rem` only. A bare `0` (`--dz-radius-none`) is projected as `0px` |
| `--dz-font-{sans,mono}` | `fontFamily` | array of names, CSS quoting dropped |
| `--dz-font-{thin…black}`, `*-font-weight` | `fontWeight` | numeric, 1–1000 |
| `--dz-leading-*`, `--dz-z-*`, `*-opacity` | `number` | unitless |
| `--dz-shadow-*` (7 of 8), `*-shadow` | `shadow` | multi-layer → array; `inner` → `inset: true`; implicit spread filled as `0px` |
| `--dz-duration-*` | `duration` | `ms` |
| `--dz-ease-*` | `cubicBezier` | four numbers; y may overshoot |

**No colour carries a `hex` fallback.** Deriving one from OKLCH requires a
gamut-mapping choice (naive clipping vs CSS Color 4 gamut mapping) that would
produce a different colour than the browser renders for out-of-sRGB values.
Shipping a silently wrong fallback is worse than shipping none.

### The 26 tokens with no `$type`

Some values have no DTCG type, and this export **does not invent one**. A token
whose `$type` cannot be resolved is invalid per the spec, so these are not
emitted as tokens at all — they are recorded under
`$extensions["com.dzup"].untyped`, keyed by the path they would have had, with
their exact CSS value and the reason:

| Group | Count | Why |
|---|---|---|
| `--dz-tracking-*`, `*-letter-spacing` | 7 | values are in `em`; `dimension` allows only `px`/`rem`, and `em` is relative to the element's own font size, so no lossless conversion exists |
| `--dz-transition-*`, `*-transition` | 10 | CSS shorthand fragments and property lists; the DTCG `transition` type models one property's duration/delay/timingFunction |
| `--dz-shadow-none` (both themes) | 2 | the `none` keyword; a DTCG shadow is an object |
| `--dz-page-hero-{bg,overlay,title-gradient}` | 3 | multi-layer gradients with `var()` fallbacks into brand-preset properties this package does not define |
| `--dz-page-hero-{title-size,padding}` | 2 | `clamp()` |
| `--dz-dialog-full-max-width` | 1 | `100vw` |
| `--dz-sidebar-section-title-text-transform` | 1 | a CSS keyword; the spec has no keyword or string type |

They are still covered by the round-trip gate: their recorded CSS value is
checked against the stylesheet like every other token. Nothing is dropped
silently. To consume them, read `--dz-*` directly — that is the ABI, and it
expresses everything.

## 3. Consuming the export

> **Marked as untested.** The two recipes below are written from the tools'
> documented interfaces. Neither Style Dictionary nor Tokens Studio is installed
> in this repository and no gate here executes them, so treat them as a starting
> point and not as a verified integration. What *is* verified is that the file
> validates against the published DTCG 2025.10 JSON Schema and round-trips
> against the shipped CSS.

### Style Dictionary v5 — *untested*

v5 reads DTCG natively.

```js
// config.js
import StyleDictionary from 'style-dictionary'

export default new StyleDictionary({
  source: ['node_modules/@dzup-ui/tokens/dist/tokens.dtcg.json'],
  platforms: {
    css: {
      transformGroup: 'css',
      buildPath: 'build/',
      files: [{ destination: 'dzup.css', format: 'css/variables' }],
    },
  },
})
```

Two things to expect, both consequences of the design above rather than bugs:

1. The generated names will be Style Dictionary's, derived from the group path
   (`--primitive-color-primary-500`). They are **not** the dzup-ui ABI. If you
   want the real names, map from
   `$extensions["com.dzup"].cssVariable` — every token carries it.
2. `semantic.light` and `semantic.dark` both appear, as ordinary groups. Filter
   to one, or emit two files.

If you only want the ABI, you do not need Style Dictionary at all — import
`@dzup-ui/tokens/css`.

### Tokens Studio — *untested*

Tokens Studio reads DTCG JSON from a file or a git sync. The export is a single
document with nested groups, so it imports as one token set. `$type` values are
spec types, and aliases use `{group.token}` syntax, which Tokens Studio
resolves. The `$extensions["com.dzup"]` payload is preserved but not interpreted
— the spec requires tools to preserve extension data they do not understand.

There is **no round-trip back into this repository**. The export is one-way:
tokens are authored in `packages/tokens/src/` as TypeScript and generated from
there. A change made in a design tool has to be re-made in the source maps, or
`yarn validate:tokens:dtcg` will fail on the next run. Automated Figma/Tokens
Studio sync is deliberately out of scope and is a separate, owner-gated packet.

## 4. Regenerating and checking

```bash
yarn generate:tokens:dtcg      # writes dist/tokens.dtcg.json (deterministic)
yarn validate:tokens:dtcg      # round-trip gate; also chained by yarn validate:all
yarn tokens:generate           # writes dist/tokens.css + DESIGN.md (unchanged by the above)
```

The round-trip gate runs with or without a built `dist/`. On a clean checkout it
reconstructs the declaration blocks from the token maps and says so, rather than
passing vacuously — CI runs `validate:all` before `yarn build`.
